Textbook walkthrough

Indentation and Blocks

Indentation is part of Python syntax. A colon after constructs such as if, for, while, def, class, try or with introduces an indented suite (block). Statements at the same indentation level belong to the same block, so changing indentation can change program logic rather than merely appearance.

Learning goal: explain why Indentation and Blocks behaves this way, apply it to a small example, and verify the result independently. Begin by being able to justify this first step: Use a colon to begin a compound statement.

Deeper walkthrough

Read Indentation and Blocks as a mechanism, not a recipe

Treat this as a sequence of observable decisions rather than one opaque command. Stage 1: Use a colon to begin a compound statement. Stage 2: Indent the statements that belong to that block consistently, conventionally with four spaces. Stage 3: Dedent to return to the surrounding block. Final checkpoint: When control flow looks wrong, inspect indentation before changing the condition itself.

How it works

Trace the mechanism step by step

  1. Use a colon to begin a compound statement.
  2. Indent the statements that belong to that block consistently, conventionally with four spaces.
  3. Dedent to return to the surrounding block.
  4. Avoid mixing tabs and spaces.
  5. When control flow looks wrong, inspect indentation before changing the condition itself.

Use deliberately

When it is appropriate

Use Indentation and Blocks when it answers a defined question in Getting Started with Python and its inputs/assumptions match the current data or program state.

Boundary conditions

When to stop or reconsider

Reconsider Indentation and Blocks when the required information is unavailable, the operation would violate a validation/data boundary, or a simpler operation answers the question more transparently.

Common mistakes

Failure modes to recognise

  • Running the operation on the wrong object/type or in the wrong environment.
  • Inferring correctness from “no exception” without checking the produced value/state.
  • Hiding a boundary case instead of making its behaviour explicit.
Verification

How to check the result

  • Trace a tiny input by hand and compare the runtime result.
  • Inspect type, value/shape and any mutation/side effect explicitly.
  • Run an edge or invalid case and confirm the exception/behaviour is deliberate.
